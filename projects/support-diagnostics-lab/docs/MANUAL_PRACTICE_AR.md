# فحوص يدوية قبل الأتمتة

نفّذ في PowerShell عندما تكون خدمة المختبر مشغّلة. اكتب توقعك أولًا.

```powershell
Resolve-DnsName localhost
Test-NetConnection 127.0.0.1 -Port 8765 -InformationLevel Quiet
Invoke-WebRequest http://127.0.0.1:8765/health -NoProxy
```

قد يكون Resolve-DnsName غير متاح على غير Windows؛ لا يلزم لتشغيل الأداة نفسها. كل فحص يختبر طبقة مختلفة. دوّن العنوان، ونتيجة TCP، ورمز HTTP ومحتوى الاستجابة. لا تكفي إشارة نجاح واحدة لتفسير كل الطبقات.

## التجارب

1. **مرجع سليم:** شغّل healthy، نفّذ الفحوص واحفظ النتائج.
2. **خدمة متوقفة:** أوقف خدمة المختبر بـCtrl+C. أعد فحص المنفذ. هل حل الاسم تغيّر؟ ماذا تستطيع استنتاجه دون القفز إلى «الجهاز تالف»؟
3. **خطأ تطبيق:** شغّل `python lab/service.py --mode unavailable`. أعد الفحوص. من المتوقع أن يعرض Invoke-WebRequest خطأ HTTP 503؛ قارن ذلك بنجاح TCP. بعد إيقافها وإعادة تشغيل healthy تحقق من الاستعادة.
4. **حل الاسم:** جرّب `Resolve-DnsName missing.support-lab.invalid`. سجّل الخطأ الفعلي؛ فرّق بين اسم غير موجود ومهلة أو تعذر الوصول إلى DNS. لا تغيّر إعدادات DNS.

بعد كل تجربة شغّل الأداة وقارنها بتفسيرك. غيّر المنفذ إلى منفذ متاح في الخادم والفاحص معًا لتبرهن أنك تفهم العلاقة. استخدم [قالب التوثيق](INCIDENT_TEMPLATE.md).

## Linux: الأدلة وحدودها

بعد تجهيز بيئة Linux شخصية، جرّب `ip -br addr` و`ip route`. وجود عنوان ومسار لا يثبت وصول الحزم أو سلامة التطبيق. استخدم `journalctl -k -b --no-pager` إذا كان journal متاحًا ولديك حق القراءة؛ عدم وجود سجل لا يساوي عدم وجود عطل.

افحص مدير الشبكة الموجود فعلًا قبل اختيار سجل NetworkManager أو systemd-networkd، وحدد وقت الحادث والخدمة المعنية. قارن الاختبار بالاسم وبالعنوان، واتصال المنفذ مع استجابة التطبيق. لا تنسب عطلًا إلى جهاز مادي من نتيجة داخل WSL أو من فشل ping وحده.

هذه إرشادات تعلم؛ سجّل المخرجات الفعلية من بيئتك ولا تنسخ نتائج متوقعة وكأنها قياس.
